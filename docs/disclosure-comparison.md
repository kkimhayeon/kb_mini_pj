# 공시 수집과 계획별 비교 (4단계)

## 변경 전후

| 항목 | 기존 | 현재 |
| --- | --- | --- |
| 공시 목록 | 최근 1년 첫 페이지, 추가 페이지가 있으면 부분 조회 | 같은 기간의 최종보고서 목록을 마지막 페이지까지 조회하고 접수번호로 중복 제거 |
| 단기차입금 전년 비교 | 서로 다른 연도 응답의 계정명 부분 일치 값 | 동일 연차보고서·연결/별도 구분·계정의 당기와 전기 금액 |
| 계획 연결 | 분야 단위 후보와 첫 번째 계획 중심 | 분야와 구체적 대상명이 유일하게 일치하는 계획 ID, 불명확하면 연결 보류 |
| 금액·일정 | 제목 기반 후속 확인 | 지원되는 양수 공시의 구조화된 항목과 RM 확인값 비교 |
| 화면·저장 | 분야별 설명 중심 | 계획별 비교 결과, 이전/이후 값, 공시 근거, 계획 ID 저장 |

## 공시 조회 범위와 실패 처리

최근 1년의 list.json을 page_count=100, last_reprt_at=Y로 조회합니다. 정정 전 원본을 별개 최신 변경으로 중복 판단하지 않도록 최종보고서 목록을 사용합니다. 각 페이지의 total_page 또는 total_count를 따라가며 접수번호를 중복 제거합니다.

뒷페이지 오류·누락, 전체 건수 변동, 유효하지 않은 항목, 반복 페이지는 이미 수집한 목록을 유지하면서 DISCLOSURES=PARTIAL로 표시합니다. 무한 조회 방지를 위해 200페이지까지만 요청하며 초과 시에도 PARTIAL입니다. 조회 전체의 일관된 서버 스냅샷이나 공시 원문 전체 검토를 보장하지 않습니다.

## 재무 비교

fnlttSinglAcntAll.json의 사업보고서(reprt_code=11011)를 사용합니다. 현재 연도부터 3년 전까지 탐색하고 각 연도에서 연결(CFS)을 먼저 조회하며 자료가 없으면 별도(OFS)를 조회합니다. 연결 조회 오류를 별도 자료 없음으로 숨기지 않습니다.

계정 ID와 재무제표 구분(BS/IS/CIS/CF)을 우선 사용하고, 지원하는 정확한 계정명으로만 보완합니다. 서로 충돌하는 중복 계정, 통화 혼합·누락, 전기 금액 누락은 임의 선택하거나 0으로 채우지 않습니다. 차입금 비교는 동일 행의 thstrm_amount와 frmtrm_amount를 사용하므로 다른 보고서의 재작성 전 수치를 혼합하지 않습니다. 응답에 statementBasis, currency, receiptNumber를 포함합니다.

## 구조화된 공시 지원 범위

현재 금액·일정 비교 대상은 다음 두 종류입니다. 일반 신규시설투자, 자금조달 등 모든 공시를 숫자로 비교하는 기능은 아닙니다.

| 공시 | API | 대상명 | 금액 | 일정 |
| --- | --- | --- | --- | --- |
| 유형자산 양수 결정 | tgastInhDecsn.json | ast_nm | inhdtl_inhprc (원) | inh_prd_inh_std |
| 타법인 주식 및 출자증권 양수 결정 | otcprStkInvscrInhDecsn.json | iscmp_cmpnm | inhdtl_inhprc (원) | inh_prd |

목록과 상세 응답은 기업코드와 접수번호가 맞는 경우에만 결합합니다. 제목에서 금액·일정을 추정하지 않습니다. 상세 조회 실패·필드 누락은 DISCLOSURE_DETAILS=PARTIAL로 표시하며 제목 기반 후보는 유지합니다. 구조화된 상세를 지원하지 않는 제목은 기존 규칙에 따라 후속 확인 대상으로 처리합니다.

## 비교 판정

RM이 확인한 사업 대상·범위와 공시 대상명에서 공백·대소문자만 정규화합니다. 같은 분야에 정확히 같은 대상명이 하나일 때만 NAME_MATCH로 연결합니다. 부동산·설비 등 일반 명칭, 유사한 이름, 동일 이름의 여러 계획은 자동 연결하지 않습니다.

- NAME_MATCH도 동일 사업임이 확정되었다는 뜻은 아닙니다. 금액·일정 차이는 NEEDS_CONFIRMATION / PENDING 후보입니다.
- 금액은 두 값과 통화가 모두 존재하고 통화가 같을 때만 비교합니다. 환율을 임의 적용하지 않습니다.
- 일정은 RM이 확인한 일·월·분기·반기·연 범위로 비교합니다. 예: 3월 계획과 3월 31일 공시는 일정 차이가 없습니다.
- 확인된 계획 스냅샷의 적용일보다 이전 공시는 HISTORICAL로 남기고 신규 변경 후보에서 제외합니다.
- 비교 가능한 금액·일정이 모두 같으면 NO_DIFFERENCE입니다. 일부 값이 없거나 완료·취소 상태 등 추가 확인이 필요하면 INSUFFICIENT입니다.
- 구체적인 비교는 comparisons에 따로 반환하므로 차이가 없는 항목도 근거와 함께 화면에서 확인할 수 있습니다.

API의 gaps에는 planId와 changes(항목별 before/after)를 추가합니다. 같은 분야의 여러 계획은 질문·답변 키도 분리합니다. 제목 기반 질문은 해당 분야 계획이 하나일 때만 상담 입력에 연결하고, 여러 계획이면 답변 원문만 저장합니다.

## 저장과 검증

gap_analysis.crm_snapshot에는 comparisons와 조회 상태, gap_result에는 명시적으로 연결된 plan_id와 changed_fields, financial_signals에는 재무 비교 기준을 저장합니다. 비교 근거에 접수번호와 원본 API 필드명을 남기며 기존 JSONB 컬럼을 활용하므로 스키마 변경은 없습니다. 원문 답변만으로 RM 확인 정보를 자동 확정하지 않습니다.

로컬 HTTP 응답 테스트로 페이지 순회·중복·실패 복구·접수번호 연결·연결/별도 대체를 검증합니다. 규칙 테스트는 계획 오연결, 통화 차이, 일정 정밀도, 과거 공시를 검증하고 프론트엔드 테스트는 비교 화면과 계획별 답변 저장을 확인합니다. 실제 OpenDART/Gemini 및 운영 PostgreSQL 연결은 별도 검증이 필요합니다.
